## What was built

- **Shared catalogue (`packages/core/src/audit`):** 71 actions in 13 categories, 17 record types, the decision actions, the before/after comparison (`auditChanges`: nested settings become dotted fields, key order ignored, one-sided values for creations and deletions), and the query/response contracts. `AuditService` is typed against it.
- **API (read-only):** `GET /audit-logs` (filters, scopes, decisions, pagination), `/audit-logs/facets`, `/audit-logs/activity`, `/audit-logs/:id` (comparison, context, record as it is now, related events), `/audit-logs/export` (CSV/XLSX, recorded as `audit.exported`); `GET /reports/attendance-summary` and its export (CSV/XLSX/PDF), `/reports/faculty-activity/export` (CSV/XLSX/PDF), each recorded as `report.exported`. A generic PDF table renderer and spreadsheet helpers serve the new reports.
- **Web:** `/audit` (all activity and decisions, filters, export), `/audit/[id]` (event detail; codes such as statuses, sources and roles shown in words), `/audit/activity` (faculty activity per staff member, export), `/reports` (attendance standing with filters and exports, faculty activity report), `/reports/download` (relays the files; refusals return to the page with the reason), Training Director dashboard cards (staff activity over 7 days with the latest staff actions; training program with week, timing and allowance), `/settings` now shows the program and the configuration history (§11.3).
- **Navigation:** "Faculty activity logs" (`audit.read`) and "Training-wide reports" (`reports.export`) are live; no "coming soon" items remain.

## Decisions taken (and why)

1. **The catalogue is the type of every audit write.** An action that is not in `AUDIT_ACTIONS` does not compile, so the log can label, group and filter everything it contains, and new modules cannot drift into private logging (§15.4).
2. **Read-only by construction.** The audit read side is a separate module with `GET` routes only; the append-only trigger from Phase 1 stays the last line of defence. Reading the log is not itself logged (it would bury the record of work); exporting it is.
3. **Default view: staff actions.** §15 is about faculty activity; students' and system events are one choice away ("Everyone"). The actor's name and role are those recorded at the time; the faculty activity summary also lists staff who did nothing and staff whose account no longer exists.
4. **"Decisions"** are approvals and rejections (account verifications, profile corrections, both students' and the faculty's swap decisions), attendance corrections, ticket outcomes, and changes to an account's status, role or permissions (§3.2 "administrative decision history").
5. **Periods are Africa/Cairo days**, converted to UTC instants on the server, like the rest of the system.
6. **The affected record (§15.3)** is looked up when an event is opened: its current label and a link when it still exists (attendance records link to their visit's attendance page), "no longer exists" otherwise; the history stays either way.
7. **Attendance standing report:** every student's finalized records in the current program, with the dashboards' rules; "at the limit" means absences equal a non-zero allowance, "over" means more. It has no date filter on purpose — the standing is program-wide, like the student's own figure. Visit-by-visit records keep their Phase 4 export.
8. **Permissions per report:** faculty hold `reports.export` and `attendance.read` by default, so they see the attendance standing; the activity report and log need `audit.read` (Training Director and Super Admin by default). The API enforces each pair; the page only hides what would be refused.
9. **Limits:** 10,000 events per log export, 5,000 students per standing report; PDFs paginate at a fixed number of rows (see Phase 4's finding).
10. **`/settings` is the training-wide settings page** ("Training settings"): readable by holders of `audit.read` too, editable as before by holders of `attendance.settings.defaults` (schedule fields stay on `/schedule`).

## Known limitations

- Search covers the actor's name, the action, the record id and the reason — not the before/after values (they are JSON; searching inside them at scale needs an index Phase 7 can decide on).
- Exported log files carry the stable action identifiers (e.g. `visit.cancelled`) with a translated category; the readable labels are in the web interface.
- The audit log has no retention or archiving policy yet: it only grows (a backup/retention recommendation belongs to Phase 7's deliverables).
- The standing report covers the current program only.

## Notes for whoever runs Phase 7

- New audit actions go in `packages/core/src/audit/catalogue.ts` first, with labels in both catalogs (`audit.actions.*`; the web unit test fails otherwise).
- Report downloads go through `/reports/download?report=…` with an allow-list of parameters per report.
- The security review should include the new routes (all `GET`, permission-guarded, rows in the matrix) and the redaction rule in `AuditService`.
