# Authentication, permissions and biometric sign-in

How people prove who they are, how the system decides what they may do, and how
biometric sign-in works. Code: `apps/api/src/auth/` (API), `apps/web/lib/auth/` and
`apps/web/proxy.ts` (web), `packages/core/src/auth/` (shared rules). Security controls and
their tests are summarized in [security-review.md](security-review.md).

## Roles

| Role                | Who                                     | Notes                                                                                                                    |
| ------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `SUPER_ADMIN`       | System administrator                    | Holds every permission, including three that can never be granted to anyone else. The last active one cannot be removed. |
| `TRAINING_DIRECTOR` | Head of field training                  | Faculty permissions plus oversight (audit, schedules, defaults, staff).                                                  |
| `FACULTY`           | Teaching staff supervising field visits | Day-to-day student, group, visit, attendance, ticket and swap work.                                                      |
| `STUDENT`           | Enrolled students                       | No staff permission; self-service actions are checked by ownership.                                                      |

Account states: `ACTIVE`, `SUSPENDED` (refused on the next request), and
`PENDING_VERIFICATION` (students only, waiting for a reviewer to link their record; they
can see only their verification page).

## Sign-in methods

| Method                       | Who                             | How                                                                                                                               |
| ---------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Email + password             | Everyone with a password        | Email is case-insensitive.                                                                                                        |
| Seat number + password       | Students with a password        | Refused for a student who has not set a password yet (§4.3) — with the same answer as a wrong password.                           |
| Emailed 6-digit code         | Accounts without a password     | First sign-in of imported students and admin-created accounts; the account must then set a password before anything else.         |
| Biometric (WebAuthn passkey) | Accounts that enrolled a device | Usernameless; see below. Password and code sign-in always remain available.                                                       |
| Password recovery            | Everyone                        | Emailed code → new password; every session ends.                                                                                  |
| Signup                       | Students                        | Four-part name, seat number, university email + emailed code. Matched to an unlinked imported record at once, or sent for review. |

Answers never reveal whether an account, a seat number or an email exists: unknown
accounts, unlinked seat numbers and wrong passwords get the same response; a suspension
is revealed only to someone who knows the password.

**Codes:** 6 digits, valid 10 minutes, 5 attempts, single use; a new code replaces the
previous one; stored as an HMAC keyed by a server secret. **Passwords:** argon2id;
10–128 characters; must not contain the email's local part or the seat number, must not
be a common password, must differ from the current one. The first Super Admin's password
is generated by `pnpm db:seed`, shown once, and must be changed at first sign-in.

## Sessions and tokens

- On sign-in the API returns an **access token** (JWT, HS256, 15 minutes; issuer
  `ftms-api`, audience `ftms`, type `access`) and a **refresh token** (JWT signed with a
  separate secret) tied to a session row.
- **Refresh tokens rotate** on every use. A token used again after rotation (beyond a
  60-second grace for parallel tabs) is treated as stolen and the session is revoked.
- Sessions last **30 days** at most; refreshing never extends them.
- Each API request re-reads the session and the account: logout, revocation, a password
  reset, removal of the biometric device that opened the session, and suspension all
  take effect on the next request.
- **The browser never holds a token.** The Next.js server stores both in `httpOnly`,
  `SameSite=Lax` cookies (`Secure` in production) and calls the API itself; the proxy
  (`apps/web/proxy.ts`) refreshes an expiring access token before rendering a page.
- The web server forwards the browser's IP to the API with `BFF_SHARED_SECRET`, so rate
  limits and audit records name the person's address, not the server's.

## Rate limits (Upstash Redis, fixed windows)

| What                                    | Limit                                                 |
| --------------------------------------- | ----------------------------------------------------- |
| Failed sign-ins per identifier          | 10 per 15 min (then even the right password gets 429) |
| Failed sign-ins per IP                  | 50 per 15 min                                         |
| Code requests per email                 | 1 per minute, 5 per hour                              |
| Code requests per IP                    | 30 per hour                                           |
| Failed codes per email / per IP         | 10 / 50 per 15 min                                    |
| Failed password changes per account     | 10 per 15 min                                         |
| Biometric options / failures per IP     | 60 / 30 per 15 min                                    |
| Check-in attempts per student           | 20 per 10 min                                         |
| Report and export downloads per account | 30 per 15 min                                         |
| New tickets / swap requests per student | 10 per hour each; 60 messages per hour                |

A refusal is 429 with `Retry-After`. If Redis is unreachable, limited actions are
refused with 503 (the limits fail closed).

## Permissions

Authorization is decided by the API on **every request**, from the database: the role,
the account state, and the effective permissions. Effective permissions = the role's
defaults + per-user `ALLOW` grants − per-user `DENY` grants. Only Training Directors and
Faculty can receive grants; grants are given by holders of `permissions.manage` (the
Super Admin) with a reason, and recorded in the audit log. The web app hides what the
API would refuse, but hiding is never the protection.

| ------------------------------ | ------------------------------------------- | :---------: | :---------------: | :-----: | :-------: |

Source of truth: `packages/core/src/auth/permissions.ts` (a test keeps the database's
`permissions` table identical). Student actions — their own profile, tickets, swap
requests, check-in, attendance history, notifications, devices — are not permissions:
they are allowed by role and limited to the student's own data.

**Enforcement in the API:** global guards run on every route — authentication (unless
the route is marked `@Public`), then `@Roles`, then `@RequirePermissions` /
`@RequireAnyPermission`; services add ownership and scope checks (a student sees only
the visits of their current group; staff see what their permissions allow). The test
suite checks every route of the running API: the public routes are exactly the reviewed
list (health, sign-in, codes, recovery, signup, biometric sign-in, the signed local-file
links, and the cron endpoint guarded by its own key), and every protected operation is run
for every role (590 cases).

**Privacy toward students:** students never see which staff member decided their
verification, profile correction, ticket or group swap (staff appear as "Training
office"); the names stay in staff views and the audit log.

## Biometric sign-in (§4.5)

- **What it is:** a platform passkey (WebAuthn) — the phone's or laptop's fingerprint or
  face unlock. The device verifies the person locally; the server receives a signature
  and stores only the credential's public key, counter, transports, backup flags, the
  authenticator model id, and a name the owner gave it. No fingerprint, face image or
  template ever reaches the server.
- **Enabling it** (`/profile` → biometric sign-in) requires a session opened with a
  password or emailed code — a biometric session cannot add another device. Options:
  platform authenticator, resident key, **user verification required**, attestation
  `none`. Up to 10 devices per account. Enrollment is audited and the owner is notified.
- **Signing in** ("Sign in with fingerprint or face") is usernameless: the browser offers
  the passkeys it holds for this site, so nothing about the account is revealed. The
  assertion must answer a fresh, single-use challenge (5 minutes) and come from a
  registered, non-revoked credential of an active account; the counter is checked.
  Failures are rate-limited per IP.
- **Removing a device** (`/profile`) takes effect at once and ends every session that
  device opened.
- **Relying party:** the web app's host from `WEB_APP_URL` (or `WEBAUTHN_RP_ID`). Browsers
  require HTTPS outside `localhost`. Changing the host invalidates enrolled devices.
- **Check-in** uses the same credentials with a separate challenge bound to the student
  **and the visit** — see [attendance-rules.md](attendance-rules.md).

## Audit

Sign-ins (success and failure), code issuance and use, password changes and resets,
biometric enrollment, use and revocation, session revocation, grants, role and status
changes are recorded in the append-only audit log — never a password, code, token,
challenge, credential id or key.
